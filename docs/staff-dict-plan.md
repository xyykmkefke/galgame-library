# 制作人员字段词典化 —— 设计评估（2026-11-27）

> 状态：**已于 2026-11-28 实施完成，v2.40.0 发布**。
> 实测节省与预估基本一致（gzip -77.7KB，预估 -78.9KB）。
> 实施中发现的**接线错误**与**断言空转**见第八节，那两条比方案本身更值得读。

## 一、问题

扩展库 `vndb-extra.js` 是数据量最大的文件，字段级 gzip 成本（单独压缩该字段的值集合）：

| 字段 | raw | gzip | 有值条数 |
| --- | --- | --- | --- |
| `al` 别名 | 338727 | **151399** | 5402 |
| `n` 标题 | 290660 | 126277 | 5737 |
| `mu` 音乐 | 186658 | 46802 | 4108 |
| `ar` 原画 | 142222 | 39470 | 5476 |
| `sc` 剧本 | 158680 | 38628 | 5377 |
| `img` 封面 | 214578 | 28335 | 5737 |
| `dev` 开发商 | 88136 | 20459 | 5737 |

`mu` + `ar` + `sc` 合计 **124.9KB gzip**，占扩展库传输量的 15%。

## 二、关键度量

制作人员姓名高度重复——同一人出现在多部作品：

- 唯一姓名 **7867** 个
- 总出现实例 **34530** 次
- **平均每人 4.39 部**

这个重复率就是可压缩空间的来源。

## 三、方案与实测收益

**方案**：把三个字段的姓名替换为「按出现频率降序排列的词典」中的 id（高频人名拿小整数，gzip 对小整数更友好），词典单独存一份。

```
// 现在
{ "sc": "丸戸史明、企画屋", "ar": "柚子奈ひよ", "mu": "松本文紀" }

// 之后（dict 为全局词典数组，id 指向其中下标）
{ "sc": [1024, 88], "ar": [3], "mu": [77] }
```

**实测**（真实数据，gzip level 9）。两种口径都量了，差异很大，实施时以**整文件口径**为准：

| 口径 | raw | gzip | 节省 |
| --- | --- | --- | --- |
| 仅三字段单独压缩 | 499032 → 302748 | 147142 → 115011 | 32131（21.8%） |
| **整个 vndb-extra.js** | 2256709 → **1862873** | 808818 → **729935** | **78883（9.8%）** |

**为什么整文件口径更大**：单字段压缩时词典与 id 数组是分开算的，跨字段的重复压不掉；
整文件一起压时，`staffDict` 与其余文本共享字典，收益叠加。所以报告收益用 78.9KB 这个数。

## 四、改动面（很小）

运行时刻意做得容易替换：

- `staffValues(item, kind)` 是唯一的读取入口（`index.html:3364`）
  ```js
  function staffValues(item, kind) {
    return String(item[kind] || '').split('、')...
  }
  ```
  只需改成「取到 id 数组 → 查词典」，其余 6 处调用点（筛选、详情、制作人员一览）全部不用动。
- 直接引用 `item.mu` 的地方只有详情页 1 处（`index.html:5374`），改走 `staffValues`。
- 生成端 `fetch-vndb-extra.mjs` 的 `STAFF_ROLE` 映射后统一编码即可（第 126/137 行）。

新作索引不含 staff 字段（已核实 1329 条全无），**只有扩展库受影响**，范围收敛。

## 四之二、断言已就绪（2026-11-27 已完成）

`check-data.mjs` 里两条守卫**已落地并通过双向验证**，实施时不需要再补：

1. **`扩展别名语言干净`** —— 用文字图案（西里尔 `\u0400-\u04ff` / 谚文 `\uac00-\ud7af` /
   泰文 `\u0e00-\u0e7f`）校验 `al`，不依赖已剥离的 lang 字段。
   反向验证：注入 `Школьные Дни` + `러브 스위츠` → 准确报 2 处并 FAIL。
2. **`制作人员词典 id 全部可解析`** —— 前瞻守卫：现在 staff 还是字符串，断言自动跳过
   （输出里不出现）；一旦改成数组就生效。校验每个 id 是整数且在 `staffDict` 范围内。
   反向验证：把某条 `sc` 改成 `[999999]` → 报「id 999999 越界（词典 7867）」并 FAIL；
   改成合法 `[1024,88]` → 输出「14961 个字段数组」全部 PASS。

**为什么这条断言必须提前写**：id 越界时 `staffValues()` 会静默返回空字符串，
表现为「某作品的剧本/原画/音乐突然消失」，不抛错、不进 bad 列表。
等出问题再补断言，等于等用户发现。


## 五、风险与不做的情况

- **不建议用「拆分文件按需加载」替代**。`state.staff` 会让制作人员参与搜索筛选，
  staff 数据不是「只在详情页用」，拆分会破坏筛选功能。
- **`al` 无法再压**。已核实：别名与自身 `n` 重复 0 例、被多作品共用仅 3 例、
  去标点后与 `py` 重合仅 0.4%（30/8038）。剩下的都是真实新增的搜索能力，该占这么大。
- **`img` 不值得动**。剥离 43 字符公共前缀 raw 省 84KB，但 **gzip 只省 5KB** —— 前缀早被压掉了。
  这条已实测过两次，不要再试。

`fetch-vndb-extra.mjs` 原写 `titles.filter((t) => t.lang !== 'en')`，
等于除英语外全收：实测会混进 ru / ko / uk / th 音译（`Школьные Дни` 这类），

## 八、实施中踩到的两个坑（比方案本身重要）

### 八之一：词典读错全局名 → 5737 条制作人员静默全空

`staffValues()` 初版读的是 `window.GL_STAFF_DICT`，而词典实际写在
`window.GL_VNDB_EXTRA.staffDict`（数据文件自带，不存在那个独立全局变量）。

后果链条：`dict` 恒为 `[]` → 每个 id 查不到姓名 → 函数返回空数组 →
扩展库 5737 条的剧本/原画/音乐**全部显示「未标注」**。而且：

- 不抛错、不进 `check-data` 的 bad 列表
- `check-data` 的「词典 id 全部可解析」守卫**照样 PASS** —— 它只校验 id 是否越界，不校验能否查到人
- `verify` 原有断言也全绿 —— 因为它们自己 `split('、')` 另算一遍，压根没走页面路径

修法：词典按「随数据走」取（`staffDictOf()`），并留独立全局变量作后路。
**教训：一份数据「存在」和「能被读到」是两件事，守卫要测后者。**

### 八之二：新增断言第一版是空转的

补了「扩展库制作人员词典可还原」断言后，反向验证（注入 `dict` 恒空）**仍然 PASS 5558/5558**。

原因：断言内部自带一份解码器去重算，读的是**正确的数据来源**，测的是「数据能否还原」，
而缺陷在「页面读错来源」。测的东西和坏的地方不是同一件事。

改法：挑一个**只在扩展库出现**的姓名，走页面真实的筛选入口（`#sk=sc&sv=`）去查。
缺陷态立刻变成 `Looseboy → 240 张 · 越界 238`（FAIL），正确态 `5 张 · 越界 0`（PASS）。

**这是本项目第四次踩「断言空转」**（前三次：长音判据恒假、季数守卫前提不成立、
verify 模板字符串吞转义）。规律一致：**断言自己算一遍 = 没测页面**。
凡涉及「页面能否正确读取数据」，判据必须经过页面的真实入口。
